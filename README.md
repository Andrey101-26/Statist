# Statist

Учебный прототип системы учёта и распределения гуманитарной помощи. Проект студентов МАИ.

**Поступление → заявка → резервирование → передача → отчёт.**

Основа постановки задачи — [социальная задача №5108 на платформе «Обучение служением»](https://обучениеслужением.добро.рф/catalog/5108). Автор задачи — ГАНОУ Курганской области «Центр развития современных компетенций». Сотрудничество с организацией, предоставление данных и внедрение пока **не согласованы**. Опубликованная потребность — источник для учебного проекта, а не подтверждение партнёрства.

## Проблема и цель

В опубликованном описании заказчик сообщает о разрозненном учёте в таблицах и бумажных журналах, разных названиях одних товаров и ручном оформлении документов. Это затрудняет получение общей картины остатков и обработку заявок. Это сведения **из описания заказчика**, а не результаты собственного исследования команды. Измерений частоты ошибок, времени обработки и объёма помощи у нас пока нет.

Цель прототипа — показать согласованный учёт поступлений, потребностей, резервов и передач, при котором одна и та же помощь не может быть зарезервирована двум получателям сверх наличия.

Предполагаемые пользователи: координатор помощи и сотрудник склада. Роли и реальные правила распределения предстоит уточнить; в первой версии разделения прав нет.

## Что работает в версии 0.1

- Обзор заявок и остатков по двум учебным складам.
- Поступление нескольких товарных позиций одной операцией.
- Создание заявки с несколькими позициями и конкретным складом.
- Проверка дефицита и резервирование **всего состава** заявки одной транзакцией. При недостатке хотя бы одной позиции резерв не создаётся.
- Отмена открытой заявки с освобождением резерва.
- Подтверждение передачи: списание со склада, закрытие заявки и запись истории.
- Журнал операций, экспорт остатков в CSV, печатный учебный лист передачи.
- Проверка форм на сервере и защита от повторного сохранения одной формы поступления/заявки. Повторная выдача блокируется статусом и ограничениями базы.

Остатки рассчитываются из движений, а резерв — из заявок в статусе «В резерве». Суммирование бутылок, упаковок и одеял в один показатель не используется.

## Запуск

Нужен Python 3.11 или новее. Команды выполняются в папке репозитория.

Windows PowerShell:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py --demo
```

Linux/macOS:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python app.py --demo
```

Откройте **http://127.0.0.1:8001**. Параметр `--port 8002` меняет порт. Для следующих запусков `--demo` не нужен. Повторный запуск с ним не перезаписывает существующие справочники и операции.

Данные хранятся в `instance/statist.sqlite3` и сохраняются между запусками. Путь можно изменить переменной `STATIST_DATABASE`. Создание чистой базы без `--demo` не добавляет справочники; экран их редактирования ещё не реализован. Для знакомства используйте демо.

Приложение слушает только `127.0.0.1`. Это локальный учебный прототип **без входа и разграничения доступа**, не готовый к размещению в интернете с реальными данными. Публикация кода на GitHub не означает публикацию работающего сервиса. GitHub Pages не исполняет сервер Python.

## Проверка на демонстрации

1. Откройте заявку №1: её состав уже зарезервирован. Убедитесь, что в остатках видны физическое наличие, резерв и доступное количество.
2. Подтвердите передачу. Физический остаток и резерв уменьшатся, доступное количество останется прежним. Откройте лист передачи.
3. Откройте заявку №2: нужно 25 одеял, на выбранном складе их 15. Попытка резерва покажет дефицит 10; ни одна позиция заявки не будет зарезервирована.
4. Примите 10 одеял на Центральный склад. Повторите резервирование заявки №2 — теперь оно возможно.
5. Для проверки освобождения резерва отмените заявку №2. Товары снова доступны, физический остаток не изменяется.
6. Скачайте CSV и сравните показатели с экраном остатков.

Это ожидаемое поведение учебного сценария, не измеренный эффект реального внедрения.

## Данные и открытые источники

Пока внешний источник используется только для постановки проблемы: [карточка №5108](https://обучениеслужением.добро.рф/catalog/5108), просмотрена 19.11.2026. Указанные там сроки реализации — 15.11–30.12.2026; приоритетный исполнитель — Курганский государственный университет. Возможность участия команды МАИ нужно уточнять отдельно.

Все склады, источники, пункты передачи, остатки и заявки в демо **сгенерированы для проверки программы**. Они не являются открытой статистикой, фактами о работе организации или сведениями о реальных получателях. Используются обычные названия пяти товаров; внешние справочники не импортировались. Неполные публичные отчёты нельзя выдавать за фактические складские остатки.

Открытые данные можно подключить позже, если у выбранного набора понятны структура, дата и условия использования. Для проверки транзакций и дефицита достаточно синтетических данных. Реальные документы, данные получателей и рабочая база не должны попадать в публичный репозиторий.

## Структура

| Файл | Назначение |
|---|---|
| `app.py` | Flask, маршруты, формы, CSV и запуск |
| `store.py` | SQLite, правила резервирования и передачи |
| `ui.py` | Серверные шаблоны интерфейса и оформление |
| `tests/test_workflow.py` | Проверки целостности учёта и веб-сценариев |

Исходный код приложения написан на Python. Разметку и оформление сервер формирует для браузера; это необходимые части веб-интерфейса. JavaScript и сборщик фронтенда не используются.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверяются дефицит без частичного резерва, конкурирующие заявки, повторные операции, отмена, сохранение данных, CSRF, экранирование ввода, полный цикл через HTTP и сверка CSV с остатками. GitHub Actions повторяет проверки на Python 3.11 и 3.12.

## Границы и следующий этап

Сейчас поддерживаются целые количества и одна единица для каждого товара. Нет партий, сроков годности, межскладских перемещений, частичных выдач, редактирования заявок, пользователей, приоритетов, маршрутизации и интеграций. После выдачи заявка неизменяема; возвраты и корректировки не реализованы. Журнал хранится в той же базе, не защищён от администратора БД и не является юридическим аудитом. Лист передачи — учебный макет, а не утверждённая форма документа.

Следующий этап — согласовать с потенциальным заказчиком справочник, единицы, формы документов, роли, правила частичной выдачи и приоритетов. Только затем добавлять соответствующие функции. Формальный паспорт и подробную документацию подготовим после уточнения границ первой версии.
